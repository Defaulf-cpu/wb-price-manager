## Общие правила для всех заданий (не удалять из промта)

Проект: `/home/user/wb-price-manager` — десктоп-приложение на Electron для управления ценами
Wildberries (цены, акции, юнит-экономика, репрайсер). Git-репозиторий (ветка `main`),
публикация на GitHub — по инструкции `docs/GITHUB.md`. Node v20.

Жёсткие ограничения проекта:

1. **Никаких внешних зависимостей и CDN.** Интерфейс — чистый JS/HTML/CSS, всё работает офлайн.
   Единственные установленные пакеты: `electron`, `electron-builder`, `jsdom` (devDeps).
   Новый код не должен требовать `npm install` чего-либо ещё. Если библиотека необходима —
   сначала обоснуйте, почему нельзя без неё.
2. **Весь текст интерфейса и комментарии — на русском.**
3. Один слой бизнес-логики: `electron/service.js` (≈60 обработчиков). Он используется и
   Electron-процессом, и dev-сервером `tools/serve.js` (тот же код отвечает на `POST /api/invoke`).
   Формат ответа обработчика: `{ ok: true, ... }` или выброшенная `WBError`
   (`electron/wb-client.js`), которая превращается в `{ ok: false, error: { message, code } }`.
4. Хранилище — `electron/store.js`: JSON-файлы в каталоге `.data` (`createStore(dir, secretBox)`).
   Секреты шифруются `safeStorage`. Новые данные — новые файлы + методы `loadX/saveX`,
   имена файлов объявляются в `electron/config.js`.
5. Расчёты экономики — `electron/economics.js` (UMD-модуль: и Node, и браузер, глобал `EC`).
   Движок репрайсера — `electron/repricer-engine.js` (глобал `RP`).
6. Renderer-глобалы: `API, S, UI, U, EC, RP, App, Views`. Порядок скриптов в
   `src/renderer/index.html` — его парсит тест `tools/uitest.js`, поэтому новый файл вьюхи
   добавляется туда же.
7. Каналы IPC: новый обработчик в `service.js` **обязательно** добавляется в массив `CHANNELS`
   в `electron/preload.js`. Белый список в `main.js` строится из `Object.keys(service.handlers)`.
8. После правки любого `.js` — `node --check <файл>`.
9. Тесты: `npm test` = `updater-flow.js` (12) + `rate-limit-flow.js` (49) +
   `repricer-flow.js` (163) + `engine-unit.js` (289) + `price-watch-flow.js` (28) +
   `stocks-flow.js` (24) + `web-server-flow.js` (18) + `tools/uitest.js` (jsdom, 613 OK).
   Прогон обязан остаться зелёным, а число проверок — не уменьшиться. `tools/uitest.js`
   поднимает jsdom, парсит `index.html` и мокает `window.fetch` → вызывает
   `service.handlers[channel]` напрямую. UI-прогон запускается с
   `--expose-gc --max-old-space-size=1600`: колонок и вкладок стало больше, прежних 1200 МБ
   не хватало на финальной отрисовке. Отдельные прогоны: `test:engine`, `test:stocks`,
   `test:ui`, `test:repricer`, `test:limits`, `test:pricewatch`, `test:web`.
10. **Лимиты WB — критично.** Категория «Статистика» и «Финансы»: 1 запрос в минуту.
    «Цены и скидки», «Календарь акций», «Контент»: 10 запросов за 6 секунд.
    Новый код не должен добавлять запросы к WB без необходимости и не должен дублировать их
    в циклах по товарам. Есть встроенный rate-limiter (`RateLimiter` в `wb-client.js`).
11. WB API из песочницы/CI недоступен — боевое поведение проверяется подменой `global.fetch`
    (см. `tools/checks/rate-limit-flow.js` и `tSizePricedGoods` в `repricer-flow.js` как образцы).
12. **Работать от последнего коммита GitHub**, а не от старой копии:
    `git clone https://github.com/Defaulf-cpu/wb-price-manager.git` и сверить `git log --oneline -1`
    с тем, что указано в задании. Агент, работавший от устаревшего коммита, присылает общие файлы
    (`service.js`, `store.js`, `package.json`, `uitest.js`) без чужих правок — их приходится
    сливать вручную, а что-то неизбежно теряется.
13. **Общие файлы присылать unified diff'ом**, а не целиком: `git diff > my.patch`
    (или `git format-patch -1`). Новые файлы можно присылать целиком. Если файл всё же
    прислан целиком — обязательно приложите diff к вашей базовой версии.
14. **Не изобретать эндпоинты и поля WB.** Тела запросов и состав ответа сверяются с
    документацией `dev.wildberries.ru`; в задании G перечислены методы, которые WB уже отключил.
15. Не переименовывать существующие каналы и не менять формат их ответа без обратной
    совместимости: на этих каналах держатся `preload.js`, веб-сервер и 700+ проверок.

Что уже реализовано (не переделывать): единый ключ + отдельные ключи категорий; честная проверка
доступа; `data:refresh-all` с фоновой догрузкой разделов, упёршихся в лимит (⏳ вместо ошибки);
фактические расходы из finance-api с поиском последнего отчёта; P&L с выбором произвольного
периода; репрайсер со стратегиями/ДЦО/коридором/лимитами и двухфазным автоциклом
(расчёт → предложение → отправка через 40 минут); черновики цен («сохранить без отправки»);
карточка товара с вкладками (`items:card`, `src/renderer/js/views/itemcard.js`);
состав акций из файла кабинета (к WB за составом не обращаемся — метод отвечает HTTP 422);
импорт XLSX/CSV собственным парсером `electron/xlsx-lite.js` (без зависимостей);
веб-версия с доступом из любой точки (`tools/web-server.js`, вход по паролю, CSRF, SSE —
задание A); наблюдатель цен витрины WB для СПП и конкурентов (`electron/price-watcher.js`,
`pricewatch:*` — задание B); страница репрайсера в стиле INDEEPA с вкладки «Товары»,
строкой на 21 колонку, очередью правок, журналами и экспортом Excel до 150 000 строк
(задание C); базовая цена из `sizes[]` для товаров с поразмерными ценами и честная
блокировка строк без данных.

### Промт (копировать отсюда)

> Сделай production-ready веб-сервер для существующего проекта Electron-приложения
> `/home/user/wb-price-manager`, чтобы тем же интерфейсом можно было пользоваться
> из браузера: с самого ПК, из локальной сети и из интернета.
>
> **Контекст.** Интерфейс — статические файлы `src/renderer/**` (чистый JS/HTML/CSS, без сборок).
> Данные и бизнес-логика — `electron/service.js`, создаётся как

> Уже есть dev-сервер `tools/serve.js` (≈200 строк): поднимает статику на `0.0.0.0:4173`,
> обрабатывает `POST /api/invoke` с телом `{ channel, args: [...] }` (`args` — МАССИВ),
> возвращает `{ ok: true, data }` / `{ ok: false, error }`, и `GET /api/events` (сейчас заглушка).
> Прочитай `tools/serve.js` и `electron/service.js` (только шапку и список обработчиков) —
> контракт менять нельзя, его используют тесты.
>
> **Что сделать.** Новый файл `tools/web-server.js` (+ при необходимости `tools/web-auth.js`)
> на встроенных модулях Node (`http`, `https`, `crypto`, `fs`, `path`, `os`, `zlib`) —
> без Express и без любых npm-пакетов. Запуск: `node tools/web-server.js` и
> `npm run web` (добавь скрипт в `package.json`, не ломая существующие).
>
> Требования:
>
> 1. **Режимы доступа** через переменные окружения и/или аргументы CLI:
>    - `--mode local` (по умолчанию) — слушать `127.0.0.1`;
>    - `--mode lan` — слушать `0.0.0.0`, доступ только из приватных диапазонов
>      (10/8, 172.16/12, 192.168/16, 127/8, fd00::/8); остальные IP отбивать 403;
>    - `--mode internet` — слушать `0.0.0.0` без ограничения по IP, но **обязательно**
>      с авторизацией (см. 2) и предупреждением в консоль о рисках.
>    Порт: `--port` / `PORT`, по умолчанию 8080.
> 2. **Авторизация.** Логин/пароль задаются переменными `WB_WEB_USER` / `WB_WEB_PASS`
>    (или `--user/--pass`); если не заданы в режиме `internet` — сервер обязан
>    сгенерировать пароль, напечатать его в консоль и не пускать никого без него.
>    Сессия — cookie `HttpOnly; SameSite=Lax; Path=/`, значение = HMAC-SHA256 от
>    идентификатора сессии секретом, который хранится в `.data/web-sessions.json`
>    (срок жизни 12 часов, возможность отзыва). Пароль хранить только как
>    `scrypt`-хеш (Node `crypto.scryptSync`, соль 16 байт) — в открытом виде нигде не сохранять.
>    Защита от подбора: не более 5 неудачных попыток с IP за 15 минут (429 + `Retry-After`).
>    Все `/api/*` и все страницы кроме `/login` требуют сессию.
> 3. **HTTPS.** Если заданы `WB_WEB_CERT` и `WB_WEB_KEY` — поднимать `https`, иначе `http`
>    с явным предупреждением. Плюс инструкция в консоли: как получить бесплатный сертификат
>    (Let's Encrypt / `mkcert` для LAN) и как открыть доступ из интернета без белого IP —
>    через туннель (Cloudflare Tunnel / Tailscale / `ssh -R`), с конкретными командами.
> 4. **CSRF и безопасность.** Для `POST /api/*` требовать заголовок `X-CSRF-Token`
>    (выдаётся вместе с сессией, хранится в теле страницы `/login` и в cookie без HttpOnly);
>    при несовпадении — 403. Заголовки: `X-Content-Type-Options: nosniff`,
>    `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Content-Security-Policy`
>    (разреши только self; учти, что интерфейс не использует внешние ресурсы).
>    Ограничь размер тела запроса 25 МБ (импорт XLSX бывает большим).
> 5. **События.** Реальный `GET /api/events` — SSE (`text/event-stream`): проксируй
>    `emit(channel, payload)` из `createService` в подключённые браузеры как
>    `event: svc:<channel>` с JSON в `data`. Интерфейс уже подписан через
>    `API.on(channel, cb)` → `window.wbApp.on('svc:'+channel)` в Electron, а в браузере —
>    прочитай `src/renderer/js/api.js` и сделай так, чтобы подписки заработали через SSE
>    (в dev-сервере сейчас заглушка, поэтому события в браузере не приходят).
>    Heartbeat каждые 25 секунд, корректное закрытие, максимум 50 подключений.
> 6. **Статика.** Отдавай `src/renderer/**` с корректными MIME, кэшем
>    (`no-cache` для html, `max-age=3600` для css/js), защитой от выхода за корень
>    (path traversal). `GET /` → `index.html`.
> 7. **Один пользователь — один экземпляр данных.** Каталог данных: `--data <dir>`,
>    по умолчанию `.data` рядом с проектом. Печатай в консоль абсолютный путь,
>    локальный адрес, адреса в LAN (из `os.networkInterfaces()`) и режим доступа.
> 8. **Живучесть.** Необработанная ошибка в обработчике не должна ронять сервер
>    (`process.on('uncaughtException')` + `unhandledRejection` — лог и работа дальше);
>    graceful shutdown по SIGINT/SIGTERM; лог запросов одной строкой
>    (время, IP, метод, путь, статус, мс) в stdout, ошибки — в stderr.
> 9. **Инструкция.** Файл `docs/WEB.md` (на русском): как запустить в трёх режимах,
>    как открыть с телефона в той же сети, как выйти в интернет через туннель
>    (пошаговые команды для Windows и Linux), как включить HTTPS, где хранятся сессии,
>    как сменить/отозвать пароль, таблица переменных окружения, раздел «безопасность»
>    (почему нельзя держать режим `internet` без пароля, что ключи WB лежат на сервере,
>    а не в браузере).
> 10. **Тесты.** Файл `tools/checks/web-server-flow.js` в стиле существующих прогонов
>     (см. `tools/checks/repricer-flow.js`): подними сервер на случайном порту в режиме

>     статика отдаётся; `/api/invoke` без сессии → 401; логин с неверным паролем → 401
>     и после 5 попыток → 429; логин с верным → cookie; `app:state` с сессией → 200 и
>     `demo:true`; POST без `X-CSRF-Token` → 403; IP вне приватной сети в режиме `lan` → 403
>     (подделай заголовок `X-Forwarded-For` только если сервер ему доверяет — иначе проверь
>     на уровне `socket.remoteAddress`, подменив его в тесте); SSE delivers событие
>     `svc:log` после вызова, который его порождает.
>     Прогон должен завершаться `process.exit(fail ? 1 : 0)` и печатать
>     «Всего проверок / пройдено / провалено» и «ИТОГ: ВСЁ ЗЕЛЁНОЕ».
>     Добавь его в `npm test` третьим шагом (после существующих двух) и в `package.json`

>

момент — это страховка для всех остальных заданий. I и J — автономные, их удобно отдать
агенту, пока основной поток занят. K полезен после того, как веб-версия уже работает.
L отложен, потому что требует профиля данных (J). N — последнее: это ужесточение уже
работающей веб-версии, оно ничего не чинит, только закрывает решения владельца.

**Три разных агента, если хочется параллельно:**

* **агент «фронтенд»** — D, затем E (строго по очереди);
* **агент «бэкенд»** — G, затем F, затем J, затем L;
* **агент «инфраструктура»** — H, затем I, затем K, затем N.

Тогда одновременно идут три ветки, и они почти не пересекаются по файлам. Всё равно присылайте
мне результат по одному: я вшиваю, прогоняю `npm test` и только потом беру следующий.

## Как присылать результат мне

**Что обязательно:**

1. `git diff > zadanie-X.patch` — unified diff по всем изменённым файлам. Если площадка не
   пропускает `.patch`, переименуйте в `zadanie-X.txt`: я проверяю содержимое, а не расширение.
   Именно так пришло задание C, и патч оказался полным — по нему удалось воспроизвести все
   восемь файлов агента байт в байт и слить их трёхсторонним слиянием.
2. Новые файлы (которых нет в репозитории) — целиком, с полным путём в имени.
3. Отчёт: что сделано, какие каналы добавлены/изменены, что НЕ сделано и почему,
   какие решения агент принял сам.
4. Вывод `node --check` по каждому изменённому `.js` и полный лог `npm test`
   (с числом проверок до и после — проверок должно стать больше, а не меньше).

**Что желательно:** описание того, что проверить вручную, и скриншот-описание интерфейса
(текстом: какая колонка что показывает).

**Чего не нужно:** архивов всего проекта и папки `node_modules`. Не присылайте общие файлы
целиком без diff — я не смогу отличить ваши правки от чужих, которых в вашей копии не было.

Файлы можно просто вложить в сообщение. Если агент отдал текст в чат, сохраните его в файл
с нужным именем (например `zadanie-D.patch`) и пришлите.
