# Веб-доступ к WB Price Manager

`tools/web-server.js` запускает тот же интерфейс и бизнес-логику, что и Electron, но через браузер. Данные и ключи WB остаются на компьютере, где работает сервер. Веб-сервер не использует Express или дополнительные npm-пакеты.

## Запуск

Из каталога проекта:

```sh
npm run web
# то же самое:
node tools/web-server.js
```

В Windows проще всего — двойной клик по **`Веб-версия (доступ из сети).bat`**: скрипт спросит
режим (только этот компьютер / локальная сеть / интернет через туннель) и порт, напомнит про
пароль и запустит сервер.

По умолчанию сервер слушает только `127.0.0.1:8080` (`local`). При первом запуске создаётся учётная запись `admin` со случайным паролем: пароль выводится в консоль **один раз**, сохраните его. Если заданы `WB_WEB_USER` и `WB_WEB_PASS`, используются они. При первом входе откроется `/login`.

### 1. Только этот компьютер — `local`

```sh
node tools/web-server.js --mode local --port 8080
```

Откройте `http://127.0.0.1:8080`. В режиме `local` сервер привязан только к loopback-интерфейсу и не принимает соединения с других устройств.

### 2. Локальная сеть — `lan`

```sh
node tools/web-server.js --mode lan --port 8080
```

Сервер слушает `0.0.0.0`, но принимает запросы только с loopback и частных адресов IPv4 (10/8, 172.16/12, 192.168/16) и IPv6 ULA (`fd00::/8`). Заголовок `X-Forwarded-For` не считается достоверным и не используется для проверки IP.

Для телефона/планшета подключитесь к той же Wi-Fi сети, посмотрите выведенный сервером адрес LAN (например, `http://192.168.1.25:8080`) и откройте его в браузере телефона. Если страница недоступна, разрешите входящие подключения к порту 8080 в брандмауэре компьютера и убедитесь, что Wi-Fi роутер не включает изоляцию клиентов. HTTP в LAN не шифрует пароль и данные — для недоверенной сети настройте HTTPS (см. ниже).

### 3. Интернет — `internet`

```sh
node tools/web-server.js --mode internet --port 8080
```

Потребуется логин и пароль. Если пароль не задан и ранее не был сохранён в каталоге данных, сервер создаст криптографически случайный и выведет его в консоль. Режим `internet` слушает `0.0.0.0` и не ограничивает IP, поэтому используйте HTTPS, задайте длинный уникальный пароль и по возможности открывайте доступ через VPN/туннель, а не напрямую через роутер.

Чтобы сменить пароль, задайте новое значение `WB_WEB_PASS` (либо `--pass`) и перезапустите сервер. Новый пароль хранится как scrypt-хеш с солью; смена пароля отзывает ранее созданные сессии. Не передавайте пароль в командной строке на многопользовательской машине: аргументы процесса могут быть видны другим локальным пользователям. Предпочтительнее переменные окружения или файл окружения с правами доступа только владельцу.

## Доступ из интернета без белого IP

Ниже примеры туннелей. Сам веб-сервер оставляйте в режиме `local` или `lan` — не пробрасывайте порт роутером напрямую без необходимости.

### Cloudflare Tunnel (Linux / Windows)

1. Установите `cloudflared` и войдите в Cloudflare, если используете именованный туннель. Для быстрой временной ссылки (Quick Tunnel) отдельная настройка домена не нужна.
2. Запустите сервер локально:

   ```sh
   # Linux/macOS
   WB_WEB_USER=admin WB_WEB_PASS='длинный-уникальный-пароль' node tools/web-server.js --mode local --port 8080
   ```

   ```powershell
   # Windows PowerShell
   $env:WB_WEB_USER = 'admin'
   $env:WB_WEB_PASS = 'длинный-уникальный-пароль'
   node tools/web-server.js --mode local --port 8080
   ```

3. Во втором терминале запустите туннель:

   ```sh
   cloudflared tunnel --url http://localhost:8080
   ```

4. Откройте выданный `https://…trycloudflare.com` адрес. Временный Quick Tunnel меняет адрес после перезапуска. Для постоянного адреса создайте именованный туннель и DNS-маршрут в панели Cloudflare.

### Tailscale

Установите Tailscale на сервер и клиентское устройство, войдите в один tailnet, затем:

```sh
node tools/web-server.js --mode local --port 8080
 tailscale serve --bg 8080
```

На клиентском устройстве откройте HTTPS-адрес, показанный командой `tailscale serve status` (или `tailscale status`). Доступ дополнительно ограничивается ACL вашего tailnet.

### SSH reverse tunnel (Linux / Windows с OpenSSH)

На компьютере с приложением запустите локальный сервер:

```sh
node tools/web-server.js --mode local --port 8080
```

Во втором терминале на компьютере с доступом к SSH-серверу/VPS:

```sh
ssh -N -R 8080:localhost:8080 user@your-vps
```

Затем откройте `http://localhost:8080` на VPS или используйте reverse proxy с HTTPS (например, Nginx + Let's Encrypt). Для публикации на внешнем интерфейсе VPS может потребоваться `GatewayPorts clientspecified` в `sshd_config` и `-R 0.0.0.0:8080:localhost:8080`; не публикуйте такой порт без HTTPS и ограничения доступа.

## HTTPS

Если заданы **обе** переменные `WB_WEB_CERT` и `WB_WEB_KEY`, сервер запускает HTTPS (TLS 1.2 или новее). Если сертификат не задан, используется HTTP и сервер явно предупреждает об этом.

### LAN: mkcert

Установите [mkcert](https://github.com/FiloSottile/mkcert), узнайте IPv4-адрес компьютера в LAN и выполните:

```sh
mkcert -install
mkcert -cert-file lan.crt -key-file lan.key localhost 127.0.0.1 192.168.1.25
```

Замените `192.168.1.25` своим LAN IP. На сервере:

```sh
# Linux/macOS
WB_WEB_CERT=./lan.crt WB_WEB_KEY=./lan.key node tools/web-server.js --mode lan --port 8080
```

```powershell
# Windows PowerShell
$env:WB_WEB_CERT = '.\lan.crt'
$env:WB_WEB_KEY = '.\lan.key'
node tools/web-server.js --mode lan --port 8080
```

Чтобы браузер телефона доверял сертификату, установите корневой сертификат mkcert на телефон согласно инструкции mkcert; иначе браузер покажет предупреждение. Не отправляйте приватный `lan.key` другим людям.

### Публичный домен: Let's Encrypt

Для домена, указывающего на сервер, можно получить сертификат Certbot (пример для Linux с Nginx):

```sh
sudo apt install certbot python3-certbot-nginx
sudo certbot --nginx -d app.example.com
```

Запуск приложения с выданными файлами:

```sh
WB_WEB_CERT=/etc/letsencrypt/live/app.example.com/fullchain.pem \
WB_WEB_KEY=/etc/letsencrypt/live/app.example.com/privkey.pem \
node tools/web-server.js --mode internet --port 8080
```

Сертификаты Let's Encrypt обновляются примерно каждые 90 дней; настройте и проверьте автоматическое обновление (`sudo certbot renew --dry-run`). Если приложение стоит за TLS-терминирующим туннелем/прокси, внешний адрес может быть HTTPS даже при HTTP между прокси и приложением — защищайте этот внутренний участок доверенной сетью.

## Данные, сессии и отзыв доступа

- Каталог приложения по умолчанию: `.data` в корне проекта. Переопределить: `--data <каталог>` или `WB_WEB_DATA`.
- Файл `web-sessions.json` внутри каталога данных содержит секрет HMAC, scrypt-хеш пароля и активные сессии. Он создаётся с правами доступа только владельцу, где это поддерживается ОС. Не публикуйте и не синхронизируйте его в общедоступное облако.
- Срок сессии — 12 часов. Cookie содержит HMAC-SHA256-токен идентификатора сессии (сам идентификатор хранится на сервере), имеет флаг `HttpOnly`, `SameSite=Lax`, `Path=/`; подпись проверяется при каждом запросе. CSRF-токен хранится отдельно в cookie без `HttpOnly`, чтобы браузерный интерфейс мог добавлять заголовок `X-CSRF-Token`.
- Выход/отзыв текущей сессии: кнопка **«Выйти»** в правом верхнем углу интерфейса (она появляется
  только в веб-версии — в Electron и в dev-сервере `tools/serve.js` сессии нет). Кнопка вызывает
  `POST /api/logout` с CSRF-заголовком, сервер удаляет сессию, а браузер возвращается на `/login`.
  То же самое из консоли: `fetch('/api/logout',{method:'POST',headers:{'X-CSRF-Token':decodeURIComponent(document.cookie.split('; ').find(x=>x.startsWith('wb_web_csrf=')).split('=').slice(1).join('='))}})`.
- Отозвать все сессии и одновременно сменить пароль: задайте новый `WB_WEB_PASS` и перезапустите. Для принудительной полной переинициализации остановите сервер и удалите `web-sessions.json`; будет создан новый пароль, если пароль не задан окружением.

## Настройки окружения и аргументы

| Назначение | Аргумент | Переменная окружения | По умолчанию |
|---|---|---|---|
| Режим доступа | `--mode local\|lan\|internet` | `WB_WEB_MODE` | `local` |
| Порт | `--port N` | `PORT` | `8080` |
| Каталог данных | `--data <dir>` | `WB_WEB_DATA` | `<проект>/.data` |
| Имя пользователя | `--user <name>` | `WB_WEB_USER` | `admin` |
| Пароль | `--pass <password>` | `WB_WEB_PASS` | случайный при первом запуске |
| TLS сертификат | `--cert <file>` | `WB_WEB_CERT` | HTTP, если не задано |
| TLS ключ | `--key <file>` | `WB_WEB_KEY` | HTTP, если не задано |
| Разрешить iframe | `--allow-framing` | `WB_WEB_ALLOW_FRAMING=1` | запрещено |
| SameSite cookie | `--samesite none\|lax` | `WB_WEB_SAMESITE=none` | `lax` |

Для TLS задайте сертификат и ключ вместе. Аргументы CLI перекрывают соответствующие переменные окружения.

### Встраивание в iframe на другом сайте

По умолчанию страница **запрещает** встраивание в iframe (`X-Frame-Options: DENY` и
`frame-ancestors 'none'` в CSP), а cookie выдаются с `SameSite=Lax`. Это правильные значения
для обычного доступа: открыли ссылку в вкладке браузера — работает.

Если же страницу нужно показать внутри чужого портала (или в окне предпросмотра песочницы),
браузер считает такие запросы сторонними и с настройками по умолчанию вход закольцуется на
`/login`. Тогда запускайте с двумя флагами:

```sh
node tools/web-server.js --mode internet --port 8080 --allow-framing --samesite none
```

* `--allow-framing` снимает `X-Frame-Options` и переключает CSP на `frame-ancestors *`;
* `--samesite none` выдаёт cookie с `SameSite=None` и **обязательным** `Secure` — без `Secure`
  браузер такое cookie просто отбросит, поэтому работает только по HTTPS (свой сертификат или
  TLS на туннеле/прокси).

Оба флага ослабляют защиту (кликджекинг и отправка cookie на чужие сайты), поэтому в
обычной работе их держать выключенными: сервер печатает отдельное предупреждение на каждый.

## Безопасность

- Не оставляйте `internet` без надёжного уникального пароля. Любой доступный из интернета сервер будет сканироваться и подвергаться попыткам подбора; после пяти неудачных попыток с одного IP включается блокировка на 15 минут. Включите HTTPS или пользуйтесь VPN/туннелем.
- Все страницы, кроме `/login`, и все `/api/*` требуют сессию. Запросы `POST /api/*` требуют CSRF-заголовок; применяются CSP, запрет фреймов, `nosniff`, `no-referrer` и лимит тела 25 МБ. CSP запрещает внешние источники скриптов/стилей/соединений; для стилей сохранён `unsafe-inline`, поскольку существующие шаблоны интерфейса широко используют атрибуты `style`. Исполняемый inline-скрипт страницы разрешён по SHA-256-хешу, а не через `unsafe-inline`.
- Ключи Wildberries и данные приложения хранятся **на машине-сервере**, а не в браузере клиента. Пользователь с веб-доступом может выполнять действия от имени этих ключей. Не раздавайте учётные данные людям, которым нельзя доверять управление кабинетом WB.
- Не помещайте `.data`, `web-sessions.json`, ключи WB или TLS private key в Git, публичные резервные копии или логи. Ограничьте права доступа к компьютеру и папке данных.
- `tools/serve.js` остаётся демо/dev-сервером без этих гарантий (ни входа, ни CSRF, ни CSP);
  для реального веб-доступа используйте `npm run web`.
- `--allow-framing` и `--samesite none` — осознанное ослабление защиты для встраивания в iframe.
  По умолчанию они выключены; включайте только на доверенном портале и по HTTPS.
